## Using it

**Build or fix something.** Assign mission (top right on every page, bottom right in the office) → pick the repo and describe it in the side panel. The manager sizes it and picks who builds it (see Routes). Work happens in the task's own git worktree. Once the checks pass, the office pushes and opens a PR (ready for review, not a draft) and asks you: **Merge**, or **Changes needed** with a comment, which goes back to the builder and updates the same PR. Merging uses the repo's merge method (Repos → Edit; squash by default), and GitHub's branch rules and required checks still apply. If GitHub refuses, the PR waits for you again with the reason. A PR you merge on GitHub yourself is noticed too. After the merge the manager writes a short retrospective.

**Routes (lanes).** *Solo* is the default. The all-rounder (Captain America on the Helicarrier deck; Opus, high effort) does the whole job in one session, like a single Claude Code session: investigates, changes the code, adds tests for behaviour changes, runs the build, lint and tests, and reviews its own diff. There's no plan to approve and no separate tester. If its diff is over 200 lines of code or 8 code files (prose doesn't count, `lanes.ts`), the reviewer checks it once before the PR opens. *Standard* is the full team: the architect plans, you approve the plan, then the coder (the UI coder for frontend work), reviewer and tester. The manager sends size L work, new screens, flows or architecture that need a written design, and risky areas (auth, payments, migrations, security) to the full team; anything with a briefing goes there too. In the mission panel, **Who builds it** overrides the manager: *Solo* (only a briefing still needs the architect) or *Full team*. If the all-rounder raises a blocker, the task joins the full team, starting with a plan. Tasks from before solo (trivial, small) run as solo. The lane shows on the card, the task page and in the Slack thread.

**Fix loops keep their context.** Review findings, failing tests or your "Changes needed" comment go back into the same coding session (Agent SDK resume), so the builder doesn't re-read the code. If the architect has planned since, or the session can't be resumed, it starts fresh. The tester writes tests only for behaviour changes. The architect always plans on its own model (Opus); on size S tasks the reviewer runs on Sonnet at medium effort (Settings → Sonnet for small tasks, on by default; applied over your Team-page agent edits).

**Epics.** A request far too big for one task (size L, several features or days of work, like "build me a chat app") isn't planned as one. The architect splits it into 2-8 milestones (breakdown.md), and you approve the split or send it back with a comment. Each milestone becomes its own task with its own thread. Milestone 1 starts right away. Each later one waits until the one before it has opened its PR, then starts from that branch, so the PRs stack. A stacked PR can only merge after the one under it; the office then points it at the default branch and merges it. A milestone whose predecessor is discarded is blocked; resuming starts it from the default branch. Milestones inherit the epic's locked skills, briefing setting and links. The epic is marked done once it's split, and its page lists the milestones. An epic is briefed before it's split (always on Auto; Never turns it off): the architect reads the repo and any reference repos, asks about the decisions that shape the whole effort, then splits with your answers. Every milestone gets those answers in its request as settled decisions, so its own briefing (if any) only asks what's specific to it.

**Slack is Fury.** There are no commands to learn. Every message you send in the DM with the bot (or that Instinct sends in the office channel) goes to Fury, the manager, on Sonnet 5.5 at low effort. Fury has no file or shell tools, only the office's own (`server/src/furyTools.ts`): list repos and tasks, task status, start a task (solo, full team or the manager's call, reference repos, links, and the files on your message), review a PR link, steer a hero, pause, stop and resume. For you alone it can also answer the architect's questions, approve or reject a gate (plan, milestones, review post, merge), discard, mark done and send a task back to the architect. Instinct's turns never get those owner-only tools, and each one checks the sender again when it runs. Instinct may start 5 tasks an hour and gets 40 messages an hour answered. A top-level message starts a thread and Fury replies in it; each thread is one conversation, kept as an Agent SDK session that is resumed on every new message (the thread-to-session map is `~/.office/slack-conversations.json`; Fury's own sessions live under `~/.office/desk`). A task Fury starts becomes that thread's task thread (status message, gate buttons and all); if the thread already has a task, the new one gets its own thread in your DM. Gate and question buttons stay: one tap is faster than typing. Tapping Reject asks what to change, and your reply in the thread is the comment. Typed answers to the architect's questions also go through Fury.

**Status, ETA, blockers.** Ask about a task in your own words and Fury reads `task_status`: the step, the hero working on it, time in the step, what waits on you (with the gate number), the blocker or note, the latest events, the PR link and an ETA worked out in code (`server/src/eta.ts`): the median duration of recent successful runs per lane and step (built-in defaults until a step has 3 runs), less the time already spent in the current step, summed over the steps the lane still has. Time you take at a gate isn't counted: it says "then it waits for you: merge". Fury reports the ETA as given and never makes one up.

**Heroes speak.** When a step ends, the hero posts a short handoff under their own name and emoji: Doctor Strange the plan, Iron Man, Loki or Captain America "done: N files, tests …", Thor the review verdict, Hulk the test result, Black Widow the cause she found, Vision the research, Hawkeye the live check. Fury answers under his own name. This needs the `chat:write.customize` scope; without it the messages post as the app with the hero's name in front. The single status message is still edited in place. Address a hero by name: "Loki, use the shared button" steers his running session (or is kept for his next run if he isn't working; Thor's current work is never interrupted by a note for someone else), and his first words after that post under his name. "Thor, what's up?" is answered by Fury from live state, without interrupting anyone. Heroes don't chat with each other.

**Read from other repos.** In the mission panel, "Read from other repos" picks up to 3 other registered repos the agents may read, for example to port code from them (in Slack: say so, "let it read beta"). Every step gets their paths and can read them with Read/Grep/Glob, cat or rg. They can't write there, cd there or run commands there, and secret files (.env and the like) stay off-limits, as in the worktree. They read each repo's main checkout as it is, so its current branch and uncommitted changes show. Epic milestones keep the epic's reference repos.

**Grill me first.** In the mission panel: Auto (the manager decides: big, design-heavy or unclear tasks), Always or Never. When it's on, the architect asks its questions in rounds before planning. Answer on the task page (one question at a time: Lock it in, an option, You decide, or your own words) or in the task's Slack thread (buttons, or reply). "Send what I've answered" and "Enough, start planning" work at any time. If nobody answers for 15 minutes the task waits in Awaiting you and frees its slot; answering picks it up again. Answers are kept in brief.md, which re-plans read. Import "grilling" on the Team page for the full interview method (Settings → Briefing picks the skill).

**Crew skills.** In the mission panel, lock skills per role; the manager picks for the roles you leave empty (with a reason, shown on the task page). Change a role's skills on the task page any time it isn't working; at plan approval the panel opens for the coder, reviewer and tester.

**Attachments.** Drop specs, screenshots or PDFs (and links) in the mission panel, or attach files to the Slack message that starts a task. The manager and architect read them; the others open them when needed.

**While it runs.** "Message the agent" sends a note to the agent that's working (or the next step). "New plan" stops and sends it back to the architect. Commands outside the repo's allow-list stop and ask you (allow once / always for this repo / deny).

**Auto-allow commands.** Settings → Auto-allow commands lets agents run commands that aren't on the allow-list without asking. Crucial commands still ask you (`crucialCommand()` in `guard.ts`): deploys, publishing, cloud, database and remote tools, curl or wget that send data, killing programs, and system installs. The guard's hard blocks apply either way (secrets, git push, writes outside the worktree). Each auto-allowed command is kept as an auto-approved gate on the task, without a Slack message.

**Live checks.** The office's agents can't reach secrets, deployed services or devices. A desktop Claude session (the `office-verifier` skill, run on a schedule) does the real-world check while the PR waits for your merge, then reports with `POST /api/tasks/:id/verification` and `{verdict: pass|fail|partial, report, stage, sha}`. `stage` is `build` (before the push), `pr` (new commits on the open PR) or `deployed` (the merge is live in production), and `sha` is the commit it checked. The report is saved as `verify.md`, shown first on the task page, and posted in the task's Slack thread. Instinct's part of the flow is in [instinct-prompt.md](instinct-prompt.md).

**Review a PR.** New task → Review a PR → paste the link (the repo must be registered). The reviewer reads the PR in a checkout of its head with read-only tools only (a PR's code never runs here). Edit or delete each comment and the summary, then post one comment review. On your own PRs, "Fix it" hands the blocking findings to a new task whose PR goes into your PR's branch. Optional: Settings → pick up review requests automatically.

**Team.** Edit any agent (model, effort, tools, prompt) or skill; reset to the built-in version anytime. "Import from Claude Code" copies skills from your Claude Code plugins and ~/.claude/skills into the office (a snapshot: a changed original shows "update available" with a diff). Attach skills to one repo's agents under Repos → Edit.

**Knowledge.** Each repo has short notes every agent reads. Retrospectives suggest notes; you add, edit or dismiss them.

**Code graph.** Repos → Edit → Code graph (Graphify). Needs `uv tool install "graphifyy[mcp]==0.9.76"`. The repo list shows tokens per architect/reviewer/debugger run with and without it, so you can tell whether it pays off.

**Usage.** No new steps start above 90% (adjustable) of the 5-hour or 7-day limit; they resume after the reset.

**Office.** The Office tab is the pixel office, filling the page (the corner button makes it full screen). Each working character carries a small name tag; the Live panel on the left lists the missions in flight and who is on duty with what they are doing right now. Hover a row to point out the character, or hover a character for its full label. A waiting bubble means a gate needs you.

## Safety model, in one paragraph

Agents run with your Claude subscription through the Agent SDK, isolated from your own Claude settings. A guard checks every tool call: writes only inside the task's worktree, no secrets (`.env`, keys, `~/.office`), no git history or GitHub commands (only the office pushes, and only `office/*` branches; merging waits for your approval), and shell commands from a per-repo allow-list with dangerous flags blocked (bundled, abbreviated or quoted). PR reviews get no shell at all. A mission's attachments folder is readable (never writable) by that task's agents only, through the Read tool. The board binds to 127.0.0.1 and rejects other sites and host names (remote access waits for phase 2's Cloudflare Access check).
